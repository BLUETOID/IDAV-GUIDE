Unit I: Introduction to Data Analytics & Lifecycle

08 Lectures  |  ST-1 Questions: Q1–7, Q17–19, Q23, Q24, Q34–38

1. Data Analytics

Definition

Data analytics is the systematic process of examining, cleaning, transforming, and modeling raw data using statistical, mathematical, and computational techniques to extract meaningful patterns, test hypotheses, and produce actionable insights that support decision-making.

Why Data Analytics Matters

Every organization generates data — from transactions, user interactions, sensors, and external feeds. Without analytics, this data is inert. Analytics converts it into competitive intelligence: it allows organizations to understand what is happening, why it is happening, what will happen next, and what the optimal response is. The McKinsey Global Institute estimates that data-driven organizations are 23 times more likely to acquire customers and 6 times more likely to retain them than non-data-driven peers.

The Four Types of Data Analytics

The four types form a maturity continuum — each succeeding type provides more foresight but requires greater analytical sophistication:

TypeQuestion AnsweredTechniqueBusiness ExampleValue
Descriptive What happened? Aggregation, summation, basic statistics, OLAP, dashboards Monthly sales report: "Q3 revenue was $4.2M, up 8% from Q2" Situational awareness
Diagnostic Why did it happen? Drill-down, correlation analysis, root-cause analysis, data mining "Q3 revenue rose because the new loyalty program increased repeat purchases by 22%" Understanding causality
Predictive What will happen? Regression, machine learning, time series forecasting, probability modeling "Q4 revenue is forecast to be $4.7M ± $0.2M with 85% confidence" Future-ready planning
Prescriptive What should we do? Optimization algorithms, simulation, decision trees, reinforcement learning "Shift $150K of TV ad spend to digital to maximize Q4 revenue; expected gain: $420K" Optimal decision-making

Data-Driven vs Intuition-Driven Decisions

Traditional managerial decisions rely on experience, intuition, and incomplete information — prone to cognitive biases (anchoring, confirmation bias, availability heuristic). Data-driven decisions use systematic evidence collected from reliable sources, processed by objective algorithms, and validated against historical outcomes. Organizations with strong data cultures reduce decision uncertainty, replicate successes systematically, and detect problems earlier.

The Analytics Value Chain

Raw data has no inherent business value. Value is created through a transformation chain:

Data → Collect & Store → Information → Clean & Organize → Knowledge → Analyze & Model → Insight → Interpret & Communicate → Decision → Act & Measure → Value

2. Sources of Data

Definition

A data source is any origin point — physical, digital, or human — from which data is systematically collected for storage, processing, and analysis.

Classification of Data Sources

CategoryDescriptionExamplesCharacteristics
Internal Sources Data generated within the organization by its own systems and processes CRM databases, ERP systems, POS transaction logs, HR records, inventory systems Readily accessible, well-structured, organization-specific context
External Sources Data obtained from outside the organization Government census data, market research reports, competitor pricing, industry benchmarks Broadens context; may require licensing, API access, or scraping
Primary Sources Data collected directly for the current analytical purpose Surveys, interviews, A/B test results, lab experiments, sensor deployments High relevance; expensive to collect; no pre-existing bias from prior use
Secondary Sources Data previously collected for another purpose, repurposed for current analysis Academic datasets, historical transaction archives, open government portals (data.gov) Low cost; may not perfectly match current analytical requirements
Machine-Generated Sources Data produced automatically by systems without direct human input Server access logs, IoT sensor streams (temperature, humidity, motion), GPS location traces, network packet headers, application event logs Very high volume; highly granular; require automated collection pipelines
Human-Generated Sources Data created by human interaction, expression, or content creation Social media posts, customer reviews, forum discussions, survey responses, call center transcripts Unstructured or semi-structured; rich qualitative content; noisy and opinionated
Web & API Sources Data harvested from public web pages or consumed via APIs Web scraping (price comparison sites), Twitter/X API, Google Trends, OpenWeather API, financial data feeds Real-time availability; requires rate-limiting management; legal and ethical considerations
Biometric & Physical Sources Data derived from physical human or environmental measurements Fingerprint scanners, retinal scans, heart rate monitors (wearables), air quality sensors, satellite imagery High precision; strong privacy regulatory requirements (GDPR, HIPAA)

Data Collection Challenges

  • Access rights and licensing: External and third-party data often require subscriptions, data sharing agreements, or API credentials. Terms of service may restrict commercial use.
  • Privacy and regulatory compliance: Personal data collection is regulated by GDPR (EU), CCPA (California), HIPAA (US health), and PDPA (India). Consent, anonymization, and data minimization principles apply.
  • Format diversity: Different sources produce data in incompatible formats (CSV, JSON, XML, Parquet, binary streams) requiring ETL transformation before unified analysis.
  • Data freshness: Stale data leads to incorrect conclusions. A pricing model trained on pre-COVID data does not reflect post-COVID market dynamics.
  • Sampling bias: If data is collected only from certain user segments (e.g., mobile users), analytics findings may not generalize to the full population.

3. Classification of Data

Classification by Structure

The most common classification divides data by the degree to which it conforms to a predefined schema:

TypeSchemaStorageQueryProportion of Enterprise DataExamples
Structured Fixed, predefined rows and columns with typed fields Relational DBMS (MySQL, PostgreSQL, Oracle) SQL ~20% Bank transaction ledger, employee HR table, flight reservation record
Semi-Structured Flexible, self-describing tags/keys; no fixed schema NoSQL document stores (MongoDB), file systems JSONPath, XPath, document queries ~10–15% JSON REST API responses, XML configuration files, HTML pages, email messages (structured header + free-text body)
Unstructured None — no predefined format Object stores (Amazon S3), HDFS, file systems Requires NLP, computer vision, or signal processing preprocessing ~65–80% Customer call audio, surveillance video, social media images, PDF contracts, medical X-rays

Classification by Measurement Scale (Stevens' Scales)

Stanley Stevens (1946) classified measurement scales into four types, each supporting different mathematical operations and statistical methods:

ScalePropertiesOperations AllowedStatistical MethodsExamples
Nominal Categories with no order or magnitude; values are just labels Equality (=, ≠); counting; mode Mode, chi-square test, frequency tables Blood type (A/B/AB/O), city name, product category, color
Ordinal Categories with a meaningful order but unequal intervals between levels Ordering (<, >); rank Median, percentiles, Spearman correlation, Mann-Whitney U Customer satisfaction (1–5 stars), education level, movie rating, pain scale (1–10)
Interval Numeric with equal intervals; no true zero (zero is arbitrary) Addition, subtraction; differences meaningful; ratios not meaningful Mean, standard deviation, Pearson correlation, t-test Temperature in °C or °F (0°C is not "no temperature"), calendar year, IQ score
Ratio Numeric with equal intervals AND an absolute zero (zero means "none") All arithmetic operations including ratios All statistical methods; geometric mean, coefficient of variation Height, weight, income, age, distance, number of transactions, duration

Additional Classifications

  • Quantitative vs Qualitative: Quantitative data is numeric and measurable (height, temperature, sales volume). Qualitative data describes qualities or characteristics (color, satisfaction category, country name). This distinction maps roughly to numerical (interval/ratio) vs categorical (nominal/ordinal) scales.
  • Cross-sectional vs Time-series vs Panel data: Cross-sectional captures many subjects at one point in time. Time-series follows one subject over many points in time. Panel (longitudinal) data follows many subjects across many time points — the richest structure.
  • Master data vs Transactional data: Master data is the core reference information that rarely changes (customer names, product catalog, geographic hierarchy). Transactional data records individual business events (orders, payments, log entries) and grows continuously.
  • Raw data vs Derived data: Raw data is collected directly from sources. Derived (computed) data is calculated from raw data — e.g., customer lifetime value computed from transaction history.

4. Characteristics of Data (Data Quality Dimensions)

Definition

Data quality is the degree to which data is fit for its intended analytical purpose. Poor quality data produces incorrect insights regardless of how sophisticated the analytics methods are — the principle "garbage in, garbage out" (GIGO) applies universally.

The Six Core Quality Dimensions

DimensionDefinitionExample of ViolationImpact on Analytics
Accuracy Data correctly represents the real-world entity or event it is supposed to describe A customer's age is recorded as 250 due to a typo (25 0 entered as 250) Biased model coefficients; incorrect predictions; false conclusions
Completeness All required data fields and records are present; no missing values Income field is blank for 30% of loan applicants in the training dataset Biased models (if missingness is non-random); reduced sample size; imputation required
Consistency The same entity has the same attribute values across all systems and at all times; no contradictions Customer address shows "Mumbai" in the CRM but "Bombay" in the billing system Incorrect joins; double-counting; reconciliation failures in reporting
Timeliness Data is available when needed and reflects the current state of the entity Inventory data updated daily but used to fulfill hourly demand spikes Stock-outs; incorrect real-time decisions; stale model predictions
Validity Data conforms to defined formats, types, ranges, and business rules A date field contains the value "32-13-2024" (impossible date) Processing errors; rejected records; unreliable aggregations
Uniqueness Each entity is recorded exactly once; no duplicate records A customer who called twice appears twice in the support ticket database, inflating complaint counts Inflated metrics; incorrect customer counts; biased segmentation

FAIR Principles for Research Data

For scientific and open data, the FAIR principles (Wilkinson et al., 2016) extend quality criteria:

  • Findable: Data has a globally unique identifier and is registered in a searchable resource. Metadata is rich enough to enable discovery.
  • Accessible: Data can be retrieved using standard protocols (HTTP, FTP); authentication is transparent and documented.
  • Interoperable: Data uses community-standard vocabularies and formats that allow integration with other datasets and tools.
  • Reusable: Data has clear licensing; metadata is rich enough that another researcher can understand how it was collected and what limitations it has.

Data Quality Management

Organizations address quality problems through: (1) Data profiling — automatically computing statistics (null rates, value distributions, cardinality) to detect issues. (2) Data cleansing — filling missing values (imputation), correcting errors, standardizing formats. (3) Data validation rules — enforcing domain constraints at the point of data entry. (4) Data governance frameworks — assigning data stewards who are accountable for quality in their domain.

5. Big Data Platform

Definition

A Big Data platform is an integrated software infrastructure designed to ingest, store, process, and analyze datasets at a scale, velocity, or variety that exceeds the capabilities of traditional relational database management systems — enabling analytics workloads from gigabytes to exabytes.

Why Traditional Systems Fall Short

LimitationTraditional RDBMSBig Data Platform Solution
ScaleVertical scaling only (bigger server); practical limit ~10 TBHorizontal scaling — add commodity servers to cluster; linear scalability
SchemaRequires fixed schema before data ingestion (schema-on-write)Schema-on-read — ingest raw data now; define structure when querying
Data typesOnly structured relational dataHandles structured, semi-structured, and unstructured data natively
Processing modelACID transactions; optimized for point queriesBatch + streaming processing; optimized for large sequential scans
CostExpensive proprietary licenses; enterprise hardwareCommodity hardware + open-source software; cloud pay-per-use

Hadoop Ecosystem Architecture

Apache Hadoop (2006) is the foundational Big Data framework. Its core components:

  • HDFS (Hadoop Distributed File System): Splits large files into 128 MB blocks distributed across cluster nodes. Each block is replicated 3 times across different nodes for fault tolerance. The NameNode manages the file namespace; DataNodes store the blocks.
  • YARN (Yet Another Resource Negotiator): The cluster resource manager — allocates CPU and memory to running applications; separates resource management from processing logic.
  • MapReduce: The programming model for batch processing. A Map function processes each record independently and emits (key, value) pairs. The framework sorts and groups by key. A Reduce function aggregates values per key. Runs in parallel across all DataNodes.
  • Hive: Translates SQL-like HiveQL queries into MapReduce or Tez jobs — enables SQL analysts to query petabyte-scale HDFS data without writing Java code.
  • HBase: A NoSQL column-family store on top of HDFS; supports low-latency random reads/writes — unlike HDFS which is optimized for large sequential reads.
  • Apache Spark: In-memory distributed processing framework that replaced MapReduce for most workloads. Spark stores intermediate results in RAM rather than writing to disk, making iterative algorithms (machine learning) 100× faster than MapReduce.

Lambda and Kappa Architectures

Lambda Architecture (Nathan Marz) runs two parallel processing pipelines: a batch layer (Hadoop/Spark on historical data, high accuracy, high latency) and a speed layer (Spark Streaming/Storm on real-time data, approximate, low latency). A serving layer merges results from both. Lambda provides both historical completeness and real-time responsiveness, but requires maintaining two separate codebases.

Kappa Architecture (Jay Kreps) simplifies Lambda by eliminating the batch layer entirely — all processing, historical and real-time, is done through a single streaming pipeline (Kafka + Flink/Spark Streaming). Historical reprocessing is handled by replaying the Kafka log. Kappa reduces complexity but requires the stream processor to handle very long retention periods.

Real-World Example

LinkedIn processes over 1 trillion events per day using Apache Kafka as the central nervous system. Data flows from hundreds of microservices into Kafka topics; Flink processes streams for real-time feed ranking and anomaly detection; Spark batch jobs process the full day's data overnight for analytics and model retraining. 6. The 5Vs of Big Data

Definition

The 5Vs framework (Doug Laney, 2001 — originally 3Vs; extended to 5Vs by IBM) characterizes the defining challenges of Big Data that distinguish it from traditional data management problems.

Detailed Explanation of Each V

1. Volume — Scale of Data

Volume refers to the sheer quantity of data generated and stored. In 2023, the global data sphere exceeded 120 zettabytes (120 × 10²¹ bytes). Facebook processes over 100 petabytes of data daily; YouTube receives 500 hours of video upload every minute. Volume necessitates distributed storage (HDFS, S3) and distributed computation (MapReduce, Spark) that spreads the data across commodity server clusters rather than a single expensive machine. The key Volume-driven architectural decision is horizontal scaling (scale out) vs vertical scaling (scale up).

2. Velocity — Speed of Data Generation

Velocity refers to the speed at which data is generated and must be processed. Twitter/X generates ~6,000 tweets/second; a modern stock exchange processes 10 million trades/second; a connected car generates 25 GB of sensor data per hour. At high velocity, batch processing is insufficient — results would be hours stale. Stream processing frameworks (Apache Flink, Spark Streaming, Storm) process data continuously as it arrives, enabling results within milliseconds. The CAP theorem trade-off: at extreme velocity, systems often sacrifice full consistency for availability and partition tolerance.

3. Variety — Diversity of Data Types

Variety refers to the range of data formats and types. A single analytics platform in a modern enterprise simultaneously handles: structured relational records (SQL), semi-structured logs and API payloads (JSON/XML), unstructured documents (PDFs, Word), images (product photos, medical scans), video (surveillance, user-generated), audio (call center recordings), and graph data (social networks, knowledge graphs). Each type requires different storage systems, preprocessing pipelines, and analysis algorithms. The polyglot persistence approach uses multiple purpose-built stores (RDBMS + document DB + graph DB + vector store) rather than forcing all data into one system.

4. Veracity — Uncertainty and Quality

Veracity refers to the trustworthiness, accuracy, and reliability of data. Big Data sources are inherently noisy: social media posts contain slang, irony, and factual errors; IoT sensors have calibration drift and measurement noise; merged datasets from different systems have inconsistent formats, duplicate records, and conflicting values. IBM estimates that poor data quality costs the US economy $3.1 trillion annually. Veracity challenges drive data quality pipelines, anomaly detection systems, data provenance tracking (maintaining a full audit trail of where data came from and how it was transformed), and confidence-weighted analytics.

5. Value — Business Worth of Data

Value is the ultimate justification for Big Data investment. Raw data has no intrinsic business value — the same petabyte of clickstream data is worthless to a company that cannot extract patterns from it and priceless to one that can predict user intent from it. Value is created through the analytics pipeline: collection → storage → processing → modeling → insight → decision → revenue/cost impact. ROI examples: Netflix saves $1 billion/year in customer retention through its recommendation system; Google's advertising auction, which runs billions of times daily, is an analytics system that generates $237 billion in annual revenue.

Figure 1: 5Vs of Big Data Pentagon. Each vertex represents one characteristic of Big Data. The dashed spokes from the center to each vertex illustrate that all five dimensions must be managed simultaneously for effective Big Data analytics.

Extended Vs

Some frameworks extend beyond 5Vs:

  • Variability: The inconsistency in data flow — velocity and meaning of data streams fluctuate over time (e.g., social media traffic spikes during breaking news events). Systems must handle bursty, non-uniform data arrival patterns.
  • Visualization: Even when data is correctly collected, processed, and modeled, results must be communicated visually to human decision-makers. The ability to present multi-dimensional analytics results in comprehensible dashboards and charts is itself a Big Data challenge.

7. Need for Data Analytics & Evolution of Analytic Scalability

Why Organizations Need Data Analytics

  • Volume problem: A mid-size e-commerce site generates millions of clickstream events daily. No human team can manually inspect these to find the pattern "users who see the blue button convert 12% better than those who see the green button." Automated analytics is the only feasible method.
  • Speed of competition: Real-time fraud detection, dynamic pricing, and personalized search results require decisions in milliseconds — faster than any human can respond. Analytics algorithms embedded in production systems make these decisions automatically at scale.
  • Non-obvious patterns: The correlation between diaper sales and beer sales on Friday evenings (a famous Walmart discovery) was invisible until market basket analysis was applied. Analytics reveals patterns that human intuition cannot perceive in high-dimensional data.
  • Risk quantification: Credit scoring, insurance underwriting, and supply chain risk assessment require probabilistic models that quantify uncertainty — not possible through subjective judgment alone.
  • Regulatory compliance: In finance (Basel III, MiFID II), healthcare (HIPAA), and environmental regulation, organizations must perform and document quantitative risk analyses. Analytics provides the audit trail and evidence base.

8. Analysis vs Reporting

Definitions

Reporting is the process of organizing and presenting historical data in a standardized, pre-agreed format to communicate what occurred during a specific period. Reports are structured, scheduled, and descriptive.

Analysis is the process of interrogating data with open-ended questions to discover causes, correlations, anomalies, and predictions. Analysis is exploratory, hypothesis-driven, and forward-looking or diagnostic.

Business Intelligence vs Business Analytics

Business Intelligence (BI) is the set of technologies and processes for collecting, integrating, and presenting historical data — primarily reporting and dashboards. BI tells you what happened. Business Analytics (BA) extends BI by applying statistical and predictive modeling techniques to explain historical outcomes and forecast future ones. BA tells you why it happened and what will happen. Organizations mature from BI (reporting) to BA (analysis) as their data capabilities and analytical skills grow.

Role in Decision-Making

Effective organizational decision-making requires both. Reporting provides the factual baseline — without accurate, timely reports, decision-makers operate blind. Analysis builds on the baseline to generate and validate hypotheses, quantify risk, and produce evidence-based prescriptions. Neither alone is sufficient: reporting without analysis produces awareness without action; analysis without reporting lacks the factual grounding that ensures analytical models reflect reality.

10. Data Analytics Lifecycle

Definition

The Data Analytics Lifecycle is a structured, iterative end-to-end framework that defines the phases an analytics project passes through — from problem definition to production deployment. It is not strictly linear; teams frequently iterate between phases as new information emerges.

Phase 1: Discovery

Objective: Define the business problem in precise, measurable terms and assess feasibility. Key activities:

  • Stakeholder interviews to understand the business question and success criteria
  • Inventory of available data sources and assessment of their relevance, quality, and access
  • Definition of the analytical objective (e.g., "predict which customers will churn in the next 30 days with at least 75% precision")
  • Risk and ethical assessment (privacy, bias, regulatory compliance)
  • Project charter and resource plan

Key output: Problem statement document; data source inventory; feasibility assessment.

Common pitfall: Defining the analytical problem too vaguely ("improve customer experience") or too narrowly (solving only one symptom of a broader problem).

Phase 2: Data Preparation

Objective: Transform raw data from diverse sources into a clean, analysis-ready dataset in an analytics sandbox. Key activities:

  • Data extraction: Pull data from operational systems, APIs, databases, and files into the analytics environment
  • Data exploration (EDA): Compute descriptive statistics; draw histograms, boxplots, scatter plot matrices; examine correlation coefficients to understand distributions and relationships
  • Data cleaning: Handle missing values (remove records, impute with mean/median/mode/model-based imputation); remove or cap outliers; fix data type errors; deduplicate records
  • Data transformation: Normalize or standardize features; encode categorical variables (one-hot encoding, label encoding); create derived features (e.g., customer age from birthdate + current date)
  • Data integration: Join tables from multiple sources on common keys; resolve schema conflicts

Key output: Clean, feature-engineered dataset ready for modeling. EDA report documenting key distributions and relationships.

Common pitfall: Inadequate EDA — proceeding to modeling without understanding the data leads to surprises (class imbalance, multicollinearity, data leakage).

Phase 3: Model Planning

Objective: Select the algorithm family, features, and evaluation strategy before building models. Key activities:

  • Map the problem type to algorithm families: classification (SVM, decision tree, logistic regression, neural network), regression (linear, polynomial, ridge), clustering (K-means, DBSCAN), time series (ARIMA, LSTM)
  • Feature selection and engineering — decide which transformed features to include
  • Define evaluation metric aligned with business objective (accuracy, AUC-ROC, RMSE, F1-score, business metric like revenue impact)
  • Design cross-validation strategy (k-fold, stratified, time-series split)
  • Determine baseline model (e.g., random classifier, mean prediction) to compare against

Key output: Model specification document; feature list; evaluation plan.

Phase 4: Model Building

Objective: Train, tune, and evaluate candidate models. Key activities:

  • Split data into training / validation / test sets (typical: 70/15/15 or 80/10/10)
  • Train multiple candidate models on the training set
  • Tune hyperparameters using grid search, random search, or Bayesian optimization on the validation set
  • Evaluate all candidates on the held-out test set using the defined metric
  • Perform error analysis: examine misclassified cases; investigate residual patterns
  • Check for overfitting: large gap between training and validation performance indicates overfitting; apply regularization, dropout, or reduce model complexity

Key output: Trained, evaluated model with performance benchmarks. Model card documenting assumptions and limitations.

Common pitfall: Data leakage — accidentally including features that contain information from the future (e.g., including the outcome variable or post-event features in training data), which causes the model to appear unrealistically accurate.

Phase 5: Communicating Results

Objective: Translate model findings into business language and secure stakeholder buy-in for deployment. Key activities:

  • Prepare visualizations that explain the model's predictions and the business impact in non-technical terms
  • Quantify the expected ROI: "This churn model identifies 65% of churners in advance; preventing half of them from churning saves an estimated $2.1M/year"
  • Clearly state model assumptions, limitations, and failure modes — do not oversell
  • Address ethical and fairness concerns: does the model produce biased outcomes for any demographic group?
  • Present alternative scenarios: what happens if the model is wrong? What is the cost of false positives vs false negatives?

Key output: Executive presentation; technical model documentation; business impact estimate.

Phase 6: Operationalization

Objective: Deploy the model to a production environment where it makes real business decisions at scale. Key activities:

  • Package the model as a REST API or batch scoring service that production systems can call
  • Integrate with operational systems (CRM, ERP, marketing automation, fraud detection platform)
  • Implement monitoring: track prediction distributions, input feature distributions (data drift), and model accuracy on labeled new data (model drift)
  • Establish retraining triggers: retrain the model when accuracy drops below a threshold or when the input distribution shifts significantly (concept drift)
  • Set up A/B testing infrastructure to measure business impact of model predictions vs the baseline

Key output: Production model endpoint; monitoring dashboard; retraining pipeline.

Common pitfall: Deploying and forgetting — models degrade silently as the real-world distribution changes. Without monitoring, a model can make harmful decisions for months before anyone notices.

Figure 2: Data Analytics Lifecycle — six phases in a cyclic flow. Arrows indicate the primary direction of progression. The cycle restarts from Phase 1 (Discovery) or Phase 2 (Data Preparation) when model performance degrades or a new business question arises.

Agile Analytics

Traditional waterfall analytics projects (complete each phase before starting the next) take months before delivering value. Agile analytics applies software development agile principles to analytics: work in 2-week sprints; deliver a minimum viable model early (even if imperfect) and iterate; prioritize features by business value; maintain close collaboration between data scientists and business stakeholders throughout. Agile analytics reduces the risk of building a technically excellent model that does not address the actual business problem.

Real-World Example

A bank applies the full lifecycle to build a credit default predictor. Phase 1: define objective — reduce defaults by 20% without increasing false rejection rate above 5%. Phase 2: collect 5 years of loan records (2M rows); impute 12% missing income values; engineer features (debt-to-income ratio, payment history trend). Phase 3: select gradient boosted trees; evaluation metric: AUC-ROC. Phase 4: train on 70%; achieve AUC 0.91 on test set; interpret with SHAP values. Phase 5: present to credit committee with risk-segment breakdown; quantify $18M/year expected savings. Phase 6: deploy as a REST API called at loan application submission; retrain quarterly; monitor input distribution daily.

ML Engineer Take trained models from data scientists and deploy them to production at scale; build serving infrastructure; implement model monitoring and retraining pipelines Software engineering, MLOps tools (MLflow, Kubeflow), Docker/Kubernetes, REST APIs, cloud platforms Data scientists, DevOps, product engineering
Database Administrator (DBA) Manage database performance, security, backup, and schema; enforce data access controls; optimize query performance SQL, query tuning, database internals (indexing, partitioning), access control, backup/recovery Data engineers, application developers
Project Sponsor Provide organizational authority, funding, and business context; prioritize analytics work against other business demands; approve and champion the project Leadership, strategic thinking, budget management, stakeholder management Project manager, executive leadership
Project Manager Coordinate timeline, resources, and stakeholder communication across the full lifecycle; identify and manage risks; remove blockers for the technical team Project management (PMP, Agile/Scrum), scheduling, risk management, communication All team members, business stakeholders

Role Interaction Summary

A successful analytics project requires all roles to work in a coordinated way. The Business Analyst identifies what needs to be solved; the Data Engineer makes the data available; the Data Scientist builds the model; the ML Engineer deploys it; the DBA secures and maintains the underlying data; the Project Manager keeps everything on schedule; and the Project Sponsor and CDO provide the organizational mandate and resources. Breakdowns at any interface — especially the Business Analyst / Data Scientist interface (misunderstood requirements) or the Data Scientist / ML Engineer interface (models that work in notebooks but not in production) — are the leading causes of analytics project failure.
